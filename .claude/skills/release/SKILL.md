# Релиз

Публикует CI, а запускает — пользователь: пуш с выросшей `mod_version` и ручной запуск CI с полем `publish` хук перед командой отдаёт ему на подтверждение («это опубликует …»). `scripts/modrinth.mjs upload` / `sync` и `gh release create` сам не запускаю — хук откажет.

## Когда поднимать версию

- **Номер версии — про код мода**, часть после `+` — про версию игры: `1.1.0+26.3`. Каждый игрок видит в лаунчере только сборки под свою версию игры.
- **Мод изменился для игрока** (исправление, возможность) → новая версия по semver: исправление — patch (`1.0.1`), возможность — minor (`1.1.0`), несовместимое (настройки, конфиг) — major. Она выходит сразу на все цели мода.
- **Новая версия Minecraft или снапшот, а мод тот же** → номер не растёт: та же версия собирается и выкладывается на новую цель — **порт**. Старые цели не трогаем: их игрокам обновлять нечего. В CHANGELOG порт не пишется.
- Опубликованное не перезаписываем и не удаляем: неудачная версия — следующий patch. Удаление ломает модпаки, которые ссылаются на файл; устаревшее прячут — статус `unlisted` (уходит из списка и лаунчеров, по прямой ссылке работает).
- Номер сборки снапшота — с номером снапшота (`1.1.0+26.4-snapshot-2`), релиза — без (`1.1.0+26.4`): они не пересекаются. Сборка снапшота, выложенная без номера снапшота, занимает номер релиза — её переименовывают на Modrinth (поле номера версии), иначе `upload` упадёт с подсказкой.

## Новая версия

1. `mods/<мод>/docs/CHANGELOG.md`: пункты `[Unreleased]` — в раздел `## [x.y.z] - YYYY-MM-DD`, сверху — пустой `## [Unreleased]`. Текст — для игроков, по-английски; он уходит и на Modrinth, и в GitHub Release.
2. `mod_version=x.y.z` в `mods/<мод>/gradle.properties`, затем `npm run sync` — имена JAR в таблице README.
3. Страница проекта — `docs/MODRINTH.md`, `docs/gallery.json` и `docs/screenshots/` (обновить — `./gradlew -p mods/<мод> updateScreenshots`, посмотреть снимки).
4. `npm run verify:changed` и `npm run build -- <мод> --all-targets`; `check-changelog` сверит раздел с `mod_version`.
5. Коммит `chore(<мод>): Выпустить x.y.z` и пуш — хук спросит подтверждение, CI опубликует все цели.

## Порт: та же версия на новую цель

После `npm run versions -- --write`, сборки всех целей и скриншот-теста новой цели (скилл `targets`):

1. Коммит каталога и пуш — CI соберёт моды под новую цель, публикации нет.
2. Ручной запуск CI с полем `publish` — по моду: `gh workflow run ci.yml -R kraineff/minecraft-mods -f publish=<мод>` (хук спросит подтверждение у пользователя) или Actions → ci → Run workflow.
3. CI соберёт мод под все цели, а выложит только те, где этой версии ещё нет: уже выложенные `upload` пропускает. Новые JAR допишутся в GitHub Release версии (нет релиза — создастся).

Код порта — текущий `main`: если с прошлой версии в моде есть заметные игроку правки, честнее выпустить новую версию, а не порт.

## Что делает CI (`ci.yml`)

План — `node scripts/ci.mjs plan`. Пуш в `main`: публикуются моды с `modrinth_id`, у которых `mod_version` выросла против прежней вершины `main` (бамп не последним коммитом пуша тоже считается; понижение — нет). Ручной запуск с `publish` — указанный мод. Только если проверки и сборки этого прогона зелёные.

1. **build** собирает и проверяет мод под каждую цель и отдаёт JAR публикуемого мода артефактом — выкладывается ровно он, второй сборки нет.
2. **publish** — по задаче на цель, без Java и Gradle: `scripts/modrinth.mjs upload` выкладывает `<мод>-x.y.z+<цель>.jar` (версии игры — `modrinth` цели из каталога, changelog — раздел CHANGELOG версии, зависимость Fabric API — из `fabric.mod.json`); уже выложенная под цель версия пропускается, номер, занятый сборкой под другие версии игры, — ошибка.
3. **release** — один раз на мод: сначала тег и GitHub Release, затем `scripts/modrinth.mjs sync` приводит проект к репозиторию (ссылки на исходники и трекер из `contact` в `fabric.mod.json`, описание из `docs/MODRINTH.md`, галерея — пересобирается, только если подписи разошлись или скриншоты менялись с прошлого тега; сборки под устаревшие пререлизы — снапшот сменился следующим или вышел релиз линии, а замена уже выложена — прячет, `unlisted`; части независимы — сбой одной не мешает остальным). Тег — `<мод>/x.y.z`, в GitHub Release — JAR, выложенные этим прогоном (у существующего релиза — дописываются).

Токен — секрет репозитория `MODRINTH_TOKEN`: PAT Modrinth с правами Create versions, Write versions (прятать устаревшие сборки) и Write projects (ссылки, описание, галерея); без нужного права Modrinth отвечает 401 «Invalid Authentication Credentials». Упала задача — исправить и `Re-run failed jobs` в том же прогоне: выложенное пропустится, а JAR для GitHub Release лежат в артефактах этого прогона (новый прогон их уже не выложит и в релиз не допишет).

Пробный прогон без записи: `node scripts/modrinth.mjs upload <мод> <цель> mods/<мод>/build/libs/<мод>-x.y.z+<цель>.jar --dry-run` — что уйдёт на Modrinth; `node scripts/modrinth.mjs sync <мод> --dry-run` — что поменяется в проекте.

## Первый релиз нового мода

1. Пользователь заводит проект на Modrinth (slug), в `gradle.properties` мода — `modrinth_id=<slug>`; `check-modjson` потребует `contact.homepage` = страница проекта.
2. Новая версия по шагам выше — или ручной запуск с `publish`, если версия уже стоит.
